# 结算材料打包与邮件外发流程（mail-delivery）

归档校验、台账完成后的交付环节：收到外发指令后，把本批结算材料按节点归集打包，通过可用邮箱通道发给指定收件人，并核对投递状态。本文件只存通用规则，不记录具体批次的主体、金额、收件邮箱或邮件会话。

## 〇、触发与批次定位（动手前先确认）

1. **触发指令**：用户要求"把结算材料发邮件 / 外发 / 打包发到某收件人"时进入本流程。
2. **定位本批**：先与用户（或台账）确认四项，缺一项先补齐，不凭文件夹名兜底：
   - 供应商简称；
   - 结算期次（年份 + 月份/季度，如 2026 年 1-3 月）；
   - 涉及项目 / 井位与对应甲方主体清单；
   - 材料在归档树中的路径（公司 → 办理月份 → 项目 → 节点）。
3. **收件人绑定（默认 + 部署确认）**：
   - 本机个人使用默认绑定收件邮箱：`hujj21@sany.com.cn`（负责人胡家俊）；外发指令未另指收件人时直接发往该地址，不再逐次询问。
   - 他人从 git 克隆本地部署后，**第一时间与负责人确认是否绑定该邮箱**；未确认前不得默认沿用，须由部署者明确指定收件地址。
   - 临时改发其他收件人、抄送、密送对象仍须本轮明确授权。
   - 地址存疑时先核对底层完整邮箱（DOM 属性 / 悬停 title / 草稿核对）；查不到就回报用户，**不进入写信、不猜测拼地址**。
4. **前置状态**：打包前对照本批缺件清单核对；请示报告尚未批复时，双章结算单、增值税专票属后续办理项，**不得作为前置缺件阻断本次外发**。

## 一、渠道判定（按顺序，不可跳步）

1. **先试飞书邮箱 CLI**（`lark-cli mail`）：
   - 取主地址：`lark-cli mail user_mailboxes profile --params '{"user_mailbox_id":"me"}'`
   - 查可访问邮箱：`lark-cli mail user_mailboxes accessible_mailboxes --params '{"user_mailbox_id":"me"}'`
2. **判定 CLI 通道不可用的信号**（命中任一即停 CLI 路径，转网页邮箱）：
   - `primary_email_address` 为空、`mailbox address not found`
   - 建草稿报错 `From address is required`
   - `accessible_mailboxes` 为空列表
   - `send_as` 返回 `permission denied: mailbox not found`
3. **禁止编造发件人地址**：通道不可用时如实报告，不用用户名拼邮箱，不硬填 `--from`。
4. CLI 不可用 → 浏览器网页版邮箱（Browser Use，`plane="bu"`）。网页邮箱登录/扫码/验证码必须交用户接管，见第四节。

## 二、打包前置（与归档目录衔接）

临时包目录按节点归集，目录命名与归档层级一致：

```
{供应商简称}{结算期次}结算材料/
├── 01_请示报告/
├── 02_合同协议/
├── 03_结算单/
├── 04_工作量确认单/
└── 05_现场佐证/
```

- **纳入**：本批请示定稿、框架合同及补充协议、各主体结算单、工作量确认单、已签认现场佐证。
- **排除**：已结算挂账的专项备查件、下期材料、旧口径参照件、未拆分待确认扫描件、其他服务商材料、缓存备份与 `.DS_Store`。
- 包名：`{供应商简称}{结算期次}结算材料.zip`；正文 / 结算单金额以对账复核值为准，两者必须一致；不含税、税额、含税、税率分列，6% / 9% / 13% 不混算。
- 附件大小：普通附件上限内直接传；超限改用邮箱中转站 / 超大附件，不硬拆材料包。

## 三、写信要素（网页邮箱）

- **收件人**：输入完整邮箱地址。昵称标签常只显示 `@` 前缀，必须核对底层完整地址（DOM 属性、悬停 title，或发送前打开草稿核对），防止误匹配到同名联系人。
- **主题**：`{供应商}{结算期次}结算材料`，控制在 50 字内。
- **正文**：首屏给含税合计；列表逐项列主体、项目、金额；简述包内目录；注明「结算单双方盖章及增值税专票，待请示报告走完审批流程后办理」。
- **附件**：定位 `input[type=file]`，用浏览器上传能力传本地绝对路径；等附件卡片出现文件名 + 大小，确认无「上传中 / 进度条」状态。

## 四、网页邮箱操作步骤（Browser Use）

1. 导航邮箱网页，`snapshot()` 观察登录态。
2. **登录阻塞**（`blocked=auth`，或出现登录 / 扫码 / 验证弹窗）：立即 `interaction.request_action`，`type=browserControl`，请用户完成登录 / 验证；返回控制后重新 `snapshot()` 确认阻塞消失，再继续。
   - 不代输账号密码、验证码、支付凭据；不关闭 / 绕过验证弹窗去找内容。
3. 点「写信 / Compose」进入写信页。
4. 填收件人 → 主题 → 正文 → 上传附件，每步后观察页面回显。
5. **发送前核对**：收件人完整地址、主题、正文金额、附件名与大小逐项确认。发送是不可逆外部动作，必须取得用户明确同意（对话中确认，或交用户在页面点发送）；草稿不等于已发送。
6. **发送后核对**：进入「已发送」箱确认邮件入列；列表可能有缓存，必要时刷新 / reload；打开邮件核对收件人、附件名大小、发送状态显示「投递成功」。
7. **未入列处理**：先查是否退回草稿箱、有无拦截 / 退信提示；状态不明不重复盲发，保留草稿交用户判断。

## 五、交付留痕（本地，不入库）

投递成功后，在本地 `output/`（已被 gitignore）追加一条外发记录，字段：

- 发送日期、收件人完整邮箱、主题、附件包名、附件份数、含税合计；
- 不记录邮箱密码、验证码、登录会话等凭据；
- 该记录随台账留在本机，不提交 git。

## 六、红线

- 不代输账号密码、一次性验证码、支付凭据；不绕过登录或人机验证。
- 不编造发件人 / 收件人邮箱；地址查不到就报「未找到」。
- 收件人 / 抄送对象未确认不发送；不自动群发、不抄送未授权对象。
- 发送类写操作先经用户确认。
- 真实结算材料、邮件会话、收件信息不进 git（`.gitignore` 已排除 pdf/xlsx/docx/zip 等）；仓库只存流程、规则、模板。
